# ConsultBae — AI Automation Assignment

Merges 3 messy CSV exports (Naukri, gig-worker, CBNexus) into one clean Postgres database,
automates skill classification with n8n + Groq, and collects audio submissions through a
small FastAPI app — all three tasks writing into the same database.

---

## Stack

- **Database**: Postgres 16 (Docker locally)
- **Merge pipeline**: Python — pandas, rapidfuzz, psycopg2
- **Automation**: n8n (Docker), Groq (`openai/gpt-oss-20b`)
- **Audio app**: FastAPI, soundfile + librosa + ffmpeg, plain HTML/JS frontend

## Setup

**1. Environment variables** — create `.env` at the repo root:
```
POSTGRES_USER=<your_username>
POSTGRES_PASSWORD=<your_password>
POSTGRES_DB=<your_db_name>
DATABASE_URL=postgresql://<your_username>:<your_password>@localhost:5432/<your_db_name>
```

**2. Start Postgres + n8n:**
```bash
docker compose up -d
```

**3. Install Python dependencies:**
```bash
pip install -r requirements.txt
```
Also requires `ffmpeg` installed locally (`brew install ffmpeg` on Mac) — used to normalize
uploaded audio before extraction.

**4. Create the schema:**
```bash
cd pythontodb
python3 init_db.py
```

**5. Run the merge pipeline (Task 1):**
```bash
python3 ingestion_pipeline.py
```
Verify:
```bash
docker exec -it postgres-db psql -U postgres -d pythonTodb -c "SELECT count(*) FROM candidates;"
```

**6. Run the n8n automation (Task 2):**
- Open `http://localhost:5678`
- Import `skillTag_workflow.json`
- Add a Postgres credential (host: `postgres`, db/user/password from `.env`)
- Add your Groq API key to the HTTP Request node's header
- Execute the workflow

**7. Run the audio app (Task 3):**
```bash
cd audio_app
uvicorn main:app --reload --port 8000
```
Open `http://localhost:8000`

## Stuck Log

Everyone gets stuck on this — here's where I did, and exactly how I got past it.

### 1. Browser-recorded audio wouldn't extract at all

Tested the audio app with a plain WAV file first and it worked fine, so I moved on. Then I
actually recorded through the browser mic and submitted it, and extraction failed instantly:
`Error opening '...webm': Format not recognised.` I'd never tested the actual recording path,
only a pre-made file — that's on me, should've tested the real flow first.

Searched "soundfile webm not supported" and found that `soundfile` wraps `libsndfile`, which
only reads WAV/FLAC/OGG/AIFF-style containers — it was never going to handle WebM/Opus, which
is what every major browser's `MediaRecorder` outputs by default. Not a bug, a wrong library
assumption on my part.

I considered forcing `MediaRecorder` to record straight to WAV instead of fixing this
server-side, but rejected it — WAV support via `MediaRecorder` isn't reliable across browsers
(Safari especially), and I didn't want my extraction pipeline's correctness depending on
which browser a submitter happened to be using. Instead I convert every upload through
`ffmpeg` to a normalized WAV before extraction runs, no matter what format it originally came
in as. Tested it against a real WebM file generated from the same source tone I'd used to
validate the original WAV path, confirmed matching results.

### 2. Candidates with no overlapping identifier weren't merging

Once the merge pipeline worked for the easy cases (same email, same phone), I found real
examples where the same person appeared once with a phone and no email, and again with an
email and no phone — nothing to directly compare, since neither record had both fields
filled in.

My first instinct was to just lower the fuzzy name-match threshold so similar names alone
could trigger a merge. I rejected that fast — the dataset actually has two different people
named similarly (Priya Singh vs Priya Saxena), and merging on name similarity alone with
nothing else to back it up would have wrongly combined them.

Instead I added city as a second corroborating signal — an exact full-name match plus a city
match together cross the merge threshold, where neither does alone. That fix immediately
created a new risk: two different people who happen to share both a name and a city, with
different emails, could now wrongly merge. I tested that exact scenario deliberately (not by
assuming the fix was safe) and added a conflict guard — if both records have a non-null email
or phone and they genuinely differ, the merge is blocked outright regardless of the name/city
score.

### 3. n8n workflow stopped after one batch instead of looping

The skill-classification flow processed the first 4 candidates successfully, then just
finished — no error, looked done, but only a fraction of ~56 candidates had actually run. I
spent a while assuming it was still a Groq API issue since that's where most of my earlier
debugging had been (rate limits, malformed JSON responses).

Screenshotted the actual node wiring and traced it manually rather than searching generically
— n8n's Loop Over Items node has two separate outputs, `done` and `loop`. My processing chain
(HTTP Request → Wait → Code → Postgres Update) was wired to `done`, which only fires once at
the very end of all iterations, instead of `loop`, which fires once per batch.

Before I found this, I considered just bumping the batch size up to squeeze more candidates
through in the one run it was doing. Rejected that — it would've processed a few more people
per run but never actually fixed the loop, just delayed hitting the same wall. Rewired `loop`
into the processing chain and connected the final Postgres Update's output back into Loop Over
Items' input to close the loop properly. Confirmed it was really iterating — not just wired
correctly on paper — by watching the batch counts change across multiple passes during an
actual run.
